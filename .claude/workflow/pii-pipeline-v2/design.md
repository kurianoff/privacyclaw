# Adaptive PII Protection: T3-First Pipeline and Surface Form Oracle

**Status**: Draft v0.1 — Structure Pass
**Scope**: Privacyclaw PII subsystem — outbound pipeline redesign + inbound variation recovery

---

## 0. Abstract

This document proposes two coordinated extensions to the Privacyclaw PII protection system.

**Part I** restructures the outbound detection pipeline so that the SLM (Tier 3) runs as a *first pass* over the raw message before Tier 1 and Tier 2 operate. This eliminates the false-positive-on-synthetics problem present in the current architecture, where T3 disambiguation runs on text that already contains format-preserving synthetic values it cannot distinguish from real PII.

**Part II** introduces the **Surface Form Oracle (SFO)** — a self-improving system that generates, scores, and learns variation hypotheses for each synthetic token. Over time, the SFO transitions from rule-based prediction to a trained mention variation model, enabling reliable inbound reversal even when the upstream LLM returns tokens in significantly altered form.

The two parts are designed to compose: Part I defines the token format and vault structure that Part II consumes.

---

## 1. Background and Motivation

### 1.1 Current Architecture Limitation

In the current pipeline, Tier 1 and Tier 2 detect PII first and generate format-preserving synthetic values (`alice.smith@example.com`, `10.142.7.3`). Tier 3 then receives a message that already contains these synthetic values and is asked to disambiguate low-confidence spans.

This creates two structural problems:

**Problem A — Synthetic contamination**: T3 sees synthetic values that are indistinguishable from real PII. It may attempt to re-replace them, producing vault corruption and broken inbound reversal chains.

**Problem B — Coverage gap**: T3's contextual understanding — its ability to detect PII from surrounding prose rather than from pattern structure — is wasted when it only sees already-processed text. The most valuable T3 detections (e.g., "safe code", unnamed numeric secrets) require the original, unmodified context.

### 1.2 Inbound Reversal Fragility

The current inbound system uses Aho-Corasick over format-preserving synthetic values. Because synthetic values resemble real content, false positive matching is a non-trivial risk. More critically, the system assumes the upstream LLM returns synthetic tokens verbatim — an assumption that does not hold reliably. LLMs routinely abbreviate names, reorder components, and drop formatting characters, causing reversal misses.

### 1.3 Design Goals

- T3 should see real PII, not synthetics
- Every token in the vault should have a unique, non-PII-resembling identifier
- Inbound reversal should degrade gracefully across a spectrum of token mangling
- The system should improve its inbound matching quality over time without manual annotation

## 2. Part I — Enhanced Outbound Pipeline

### 2.1 Token Format

All synthetic replacements, regardless of which tier detected the original PII, use a unified token format:

```
<pii id="TOKEN_ID">DISPLAY_VALUE</pii>
```

**`TOKEN_ID`**: A short (8-character) base62 hash derived from `HMAC(conversation_id + entity_index)`. Opaque, non-guessable, collision-resistant within a conversation.

**`DISPLAY_VALUE`**: A realistic synthetic value generated by the existing `synth.rs` machinery (format-preserving per entity type). This preserves the upstream LLM's ability to reason about the entity (a name stays a name, a phone stays a phone). The display value is never empty.

**Example**:
```
<pii id="a3f9b2c1">Maria Blinke</pii>
<pii id="d7e1f04a">555-0142-8833</pii>
<pii id="b2c8a91e">921091</pii>
```

**Why XML tags over §§**: LLMs are trained on HTML/XML at massive scale and demonstrate strong tag-preservation behavior. The `id` attribute provides a secondary lookup key independent of display value content, enabling cascade matching on inbound (see §2.6).

### 2.2 Outbound Pipeline — Overview

```
Raw user message
       │
       ▼
┌──────────────────────────────┐
│  STAGE 1: T3 First Pass      │  SLM sees real PII, full context
│  POST /replace               │
│  → modified_text             │
│  → replacement_pairs[]       │
└──────────────┬───────────────┘
               │  vault ← Stage 1 pairs
               ▼
┌──────────────────────────────┐
│  STAGE 2: T1 + T2            │  Operate on T3-modified text
│  Skip spans inside <pii>     │  Only unmapped PII remains
│  T1: regex detection         │
│  T2: GLiNER NER (async)      │
└──────────────┬───────────────┘
               │  spans_t1, spans_t2 (merged)
               ▼
┌──────────────────────────────┐
│  STAGE 3: T3 Disambiguation  │  Optional; for low-confidence spans
│  POST /disambiguate          │  (confidence < θ_disambig)
└──────────────┬───────────────┘
               │  confirmed spans
               ▼
┌──────────────────────────────┐
│  Replacement + Vault Write   │  Single atomic pass
└──────────────┬───────────────┘
               │
               ▼
       Modified message
     (all PII → <pii> tokens)
               │
       ┌───────┴────────┐
       │                │
       ▼                ▼
  Upstream LLM     SFO Hypothesis
  (with system     Generation
   instruction)    (parallel, §4.1)
```

### 2.3 Stage 1 — T3 First Pass

#### 2.3.1 SLM API Change

The current T3 sidecar exposes `/disambiguate`. Stage 1 requires a new endpoint:

```
POST /replace
Body: { "text": "...", "conversation_id": "..." }

Response: {
  "modified_text": "...",
  "replacements": [
    {
      "original": "Anne Nicole",
      "display_value": "Maria Blinke",
      "entity_type": "person_name",
      "token_id": "a3f9b2c1",
      "start": 11,
      "end": 22
    },
    ...
  ]
}
```

**Critical design constraint**: The SLM must return an explicit `replacements` array with `original` spans. The proxy must not attempt to infer mappings by diffing `text` vs `modified_text` — diffing is fragile against LLM reformatting of surrounding prose.

#### 2.3.2 What T3 Detects That T1/T2 Cannot

T3's value in Stage 1 lies in contextual, pattern-free detection:

| Example input | Detection | Why T1/T2 miss it |
|---|---|---|
| `my safe code is 378546` | `378546` as secret | No regex pattern for "safe codes" |
| `call me at 3334445555` | phone (no separator) | Locale/format not in T1 patterns |
| `the account ends in 4821` | partial card fragment | Below T1 minimum digit count |
| `John works at Acme Corp` | `John` as person | No NER label match without T2 |

#### 2.3.3 Vault Write — Stage 1

For each replacement pair returned by T3:
```
vault.insert(
  token_id:      "a3f9b2c1",
  original:      "Anne Nicole",
  display_value: "Maria Blinke",
  entity_type:   person_name,
  tier:          T3,
  confidence:    1.0
)
```

### 2.4 Stage 2 — T1 + T2 on T3-Modified Text

#### 2.4.1 Span Exclusion

T1 and T2 receive the T3-modified text with a set of **excluded ranges** — the character spans occupied by `<pii ...>...</pii>` tokens already inserted by Stage 1. Any detected span that overlaps an excluded range is discarded.

Formally, let `E = { [s_i, e_i] }` be the set of excluded ranges. A new span `[s, e]` is accepted iff:

```
∀ [s_i, e_i] ∈ E :  e ≤ s_i  OR  s ≥ e_i
```

#### 2.4.2 Tier Execution

T1 (regex) runs synchronously. T2 (GLiNER ONNX) runs concurrently via `tokio::spawn`. Both receive the same excluded range set. Spans are merged after both complete, with overlap deduplication by highest confidence:

```
merged = deduplicate(spans_t1 ∪ spans_t2, strategy=highest_confidence)
```

#### 2.4.3 Synthetic Generation for T1/T2 Detections

T1/T2 detections use the existing `synth.rs` format-preserving generator for `DISPLAY_VALUE`. The `TOKEN_ID` is assigned from the same HMAC scheme as Stage 1. The token is formatted identically: `<pii id="TOKEN_ID">DISPLAY_VALUE</pii>`.

### 2.5 Stage 3 — T3 Disambiguation (unchanged role, new input)

Low-confidence spans from the merged T1+T2 set (confidence < `θ_disambig`, default 0.7) are sent to `/disambiguate`. The existing API contract is preserved. Confirmed spans proceed to vault write; rejected spans are dropped.

Because Stage 1 has already removed high-value contextual PII, Stage 3's disambiguation burden is reduced — it now operates primarily on borderline NER detections (ambiguous names, organizations, locations).

### 2.6 Inbound Reversal

#### 2.6.1 Token Structure as Reversal Advantage

The `<pii id="TOKEN_ID">DISPLAY_VALUE</pii>` format provides **two independent lookup keys**: the `TOKEN_ID` and the `DISPLAY_VALUE`. Inbound matching uses a cascade:

```
Inbound SSE stream
       │
       ▼
┌─────────────────────────────────┐
│  Level 1: Full token match      │
│  <pii id="a3f9b2c1">Maria Blinke</pii>  → vault[a3f9b2c1].original
└──────────────┬──────────────────┘
               │ miss
               ▼
┌─────────────────────────────────┐
│  Level 2: ID-only match         │
│  <pii id="a3f9b2c1">...</pii>   → vault[a3f9b2c1].original
└──────────────┬──────────────────┘
               │ miss
               ▼
┌─────────────────────────────────┐
│  Level 3: Display value match   │
│  <pii id="?">Maria Blinke</pii> → vault.lookup_by_display("Maria Blinke")
└──────────────┬──────────────────┘
               │ miss
               ▼
┌─────────────────────────────────┐
│  Level 4: Hypothesis match      │
│  <pii id="?">M. Blinke</pii>    → SFO hypothesis lookup (§4.3)
└──────────────┬──────────────────┘
               │ miss
               ▼
┌─────────────────────────────────┐
│  Level 5: Private-namespace     │
│  Aho-Corasick on synthetic      │
│  value corpus (no <pii> wrapper)│
└─────────────────────────────────┘
```

#### 2.6.2 Streaming Buffer

The inbound `ReplacementBuffer` is adapted to scan for `<pii` as an opening trigger. The buffer accumulates bytes until `</pii>` is seen, then attempts cascade matching. Maximum holdback window = longest possible `<pii ...>...</pii>` token in the vault (bounded by `TOKEN_ID` length + max display value length).

#### 2.6.3 Upstream LLM Instruction

A system message fragment is injected into every forwarded request when PII mode is active:

> *The user's message contains `<pii id="...">...</pii>` elements. These are opaque placeholders for sensitive values. You must treat the content inside each `<pii>` element as a single atomic unit and reproduce it verbatim — including the XML tags and `id` attribute — whenever you reference or repeat that value. Never rephrase, abbreviate, or split a `<pii>` element across multiple tokens.*

This instruction relies on LLM XML-preservation behavior rather than delimiter novelty, making it substantially more robust than §-based instructions.

## 3. Part II — Surface Form Oracle (SFO)

### 3.1 Overview

The Surface Form Oracle is a subsystem that runs **in parallel with the upstream LLM call** for each request. It takes the set of `<pii>` tokens in the outbound message and generates a set of **hypotheses** — predicted surface forms the upstream LLM might return. These hypotheses are stored in the vault and used to extend inbound Level 4 matching.

Over time, as real inbound responses confirm or falsify hypotheses, the SFO learns which transformations are common for each entity type, and eventually trains a lightweight model to replace rule-based generation.

### 3.2 Hypothesis Structure

```
Hypothesis {
    hypothesis_id:     UUID
    token_id:          String          // vault entry this hypothesis belongs to
    entity_type:       EntityType      // person_name, phone, email, ...
    transformation:    TransformLabel  // first_name_only, initial_surname, ...
    surface_form:      String          // the predicted variation string
    confidence:        f32             // prior probability [0.0, 1.0]
    score:             f32             // starts at 0.0, updated on observation
    observation_count: u32
    first_generated:   Timestamp
    last_observed:     Option<Timestamp>
    source:            HypothesisSource  // RuleBased | SLM | LearnedModel
}
```

### 3.3 Transformation Taxonomy

Transformations are **named, reusable labels** that generalize across token values. A model trained on `first_name_only` for `Maria Blinke` can apply the same transformation to `John Smith` without retraining.

#### Person Names
| Label | Example: `Maria Blinke` |
|---|---|
| `verbatim` | `Maria Blinke` |
| `first_name_only` | `Maria` |
| `surname_only` | `Blinke` |
| `initial_surname` | `M. Blinke` |
| `surname_first` | `Blinke, Maria` |
| `initials` | `M.B.` |
| `lowercase` | `maria blinke` |
| `uppercase` | `MARIA BLINKE` |
| `honorific_prefixed` | `Ms. Blinke` |

#### Phone Numbers
| Label | Example: `555-0142-8833` |
|---|---|
| `verbatim` | `555-0142-8833` |
| `no_separators` | `55501428833` |
| `dotted` | `555.0142.8833` |
| `spaced` | `555 0142 8833` |
| `last_four` | `8833` |
| `parenthesized` | `(555) 0142-8833` |

#### General / Cross-type
| Label | Description |
|---|---|
| `verbatim` | Exact copy |
| `lowercase` | All characters lowercased |
| `uppercase` | All characters uppercased |
| `truncated_N` | First N characters only |
| `noise_added` | Minor punctuation or spacing variation |
| `omitted` | LLM referenced entity without repeating token |

### 3.4 Hypothesis Generation

When the outbound message is dispatched to the upstream LLM, a parallel async task is launched:

```
for each <pii> token in outbound_message:

    hypotheses = []

    // Rule-based generation (always)
    hypotheses += RuleEngine.generate(token.entity_type, token.display_value)

    // SLM-augmented generation (when T3 is available)
    if t3_available:
        slm_suggestions = POST /hypothesize {
            token_id: token.token_id,
            entity_type: token.entity_type,
            display_value: token.display_value,
            context: outbound_message_excerpt
        }
        hypotheses += slm_suggestions

    vault.store_hypotheses(token.token_id, hypotheses)
```

The `/hypothesize` SLM endpoint is a third T3 mode alongside `/replace` and `/disambiguate`. It returns a list of `(surface_form, transformation_label, prior_confidence)` tuples.

### 3.5 Scoring System

#### 3.5.1 Initial Scores

All hypotheses start at `score = 0.0`. The `confidence` field carries the prior probability from the generating source (rule engine or SLM), but does not affect routing until enough observations accumulate.

#### 3.5.2 Score Update on Observation

When the inbound stream matches a hypothesis (Level 4 cascade match):

```
score_new = score_old + α × (1.0 - score_old)
```

Where `α` is a learning rate parameter (default: 0.3). This is an exponential moving average that bounds scores to `[0, 1)` and dampens over-fitting to early observations.

#### 3.5.3 Temporal Decay

Hypothesis scores decay over time to reflect that LLM behavior can shift across model versions:

```
score_decayed = score × e^(-λ × Δt)
```

Where `λ` is a decay constant (default: half-life of 30 days) and `Δt` is time since last observation in days.

#### 3.5.4 Routing Thresholds

| Score range | Routing behavior |
|---|---|
| `score ≥ θ_auto` (default 0.7) | Auto-substitute on inbound match |
| `θ_confirm ≤ score < θ_auto` (default 0.3–0.7) | Flag for SLM confirmation before substitution |
| `score < θ_confirm` | Log as candidate; no substitution |
| No observation for > `T_prune` (default 90 days) | Hypothesis pruned from vault |

### 3.6 Feedback Loop and Training Data Collection

Each inbound response produces labeled training records:

```
TrainingRecord {
    entity_type:        EntityType,
    display_value:      String,       // the synthetic sent to LLM
    observed_form:      String,       // what came back
    transformation:     TransformLabel,  // matched hypothesis label, or "unknown"
    matched:            bool,
    conversation_id:    String,       // for grouping multi-turn patterns
    upstream_model_id:  String        // to segment by LLM version
}
```

Records where `transformation = "unknown"` (inbound form was not covered by any hypothesis) are the highest-value training signal — they represent gaps in the hypothesis set.

Training records are written to a local append-only NDJSON log, partitioned by `entity_type`. No PII is logged: `display_value` and `observed_form` contain only synthetic values.

### 3.7 The Mention Variation Model

#### 3.7.1 Problem Statement

Given:
- `entity_type` — the semantic class of the token
- `display_value` — the synthetic value sent to the upstream LLM
- `context` — a window of the outbound message surrounding the token

Predict:
- A ranked list of `(surface_form, probability)` pairs representing how the upstream LLM might return the token

#### 3.7.2 Development Stages

**Stage 0 — Rule engine** (day one, no training data required)
Morphological rule tables per entity type. Handles `verbatim`, `lowercase`, `first_name_only`, `no_separators`, etc. Fast, deterministic, no ML dependency.

**Stage 1 — Frequency-weighted rules** (~1k training records)
Rule outputs are ranked by observed frequency from the training log. Rare transformations demoted; frequent ones promoted. Still no ML model — just a scored lookup table.

**Stage 2 — Fine-tuned seq2seq** (~5k–10k training records)
A small encoder-decoder model (T5-small, ~60M parameters, or FLAN-T5-small) fine-tuned on `(entity_type, display_value, context) → surface_form` pairs. Trained offline, served as a sidecar. Replaces the rule engine for hypothesis generation while the rule engine remains as fallback.

**Stage 3 — Entity-type specialized models** (~50k+ records)
Separate fine-tuned checkpoints per `entity_type`. Person name variations are structurally different from phone number variations; specialized models outperform a single general model.

#### 3.7.3 Model Architecture

```
Input:
  [ENTITY_TYPE] [SEP] display_value [SEP] context_window

Encoder: T5-small transformer stack

Decoder: Autoregressive generation of surface form candidates

Output (beam search, beam=8):
  [
    { surface_form: "M. Blinke",   score: 0.82 },
    { surface_form: "Blinke",      score: 0.71 },
    { surface_form: "Maria",       score: 0.68 },
    { surface_form: "M.B.",        score: 0.41 },
    ...
  ]
```

Training objective: minimize cross-entropy over observed surface forms, weighted by observation frequency.

#### 3.7.4 Inference Timing

The mention variation model runs as a third parallel task alongside the upstream LLM call and the existing SFO hypothesis generation:

```
dispatch_to_upstream_llm(modified_message)           ─┐
generate_hypotheses_rule_engine(tokens)               ─┤  concurrent
generate_hypotheses_mention_variation_model(tokens)   ─┘

await first_sse_chunk_from_upstream
// hypotheses already in vault before inbound begins
```

## 5. Open Questions (to resolve in next pass)

1. **Token ID collision**: Is 8-char base62 (62^8 ≈ 218 trillion) sufficient within a single conversation? Or should it be scoped globally across the vault registry?

2. **T3 sidecar versioning**: The three new T3 endpoints (`/replace`, `/disambiguate`, `/hypothesize`) must be versioned. What is the minimum sidecar API version required, and how does the proxy degrade when it connects to an older sidecar?

3. **Private namespace synthetic values**: Should the `DISPLAY_VALUE` inside `<pii>` come from a private namespace (e.g., `@privacyclaw.internal` emails, `555-0xxx` phones) to enable Level 5 matching without delimiter dependency? Or is the `<pii>` wrapper reliable enough to make this unnecessary?

4. **Multi-turn conversations**: The vault is keyed per conversation. If the upstream LLM references a `<pii>` token from turn 1 in its turn 3 response, the `<pii>` token must still be present in the vault. Is the current vault TTL (24 hours) sufficient for long-running agentic sessions?

5. **MVM training pipeline**: Who triggers retraining? What is the minimum record count to promote from Stage 0 to Stage 1, and from Stage 1 to Stage 2? Is training done locally on the user's machine, or is it a centralized process?

6. **Hypothesis pruning policy**: Hypotheses with `score < θ_confirm` after `T_prune` days are pruned. But what if a transformation is rare (appears once every 100 conversations) yet semantically important? Should observation sparsity factor into pruning decisions independently of score?

7. **`omitted` transformation handling**: When the LLM refers to an entity without repeating the token at all ("I'll send the details to your contact"), there is no inbound token to match. How does the system detect and handle omitted references?
